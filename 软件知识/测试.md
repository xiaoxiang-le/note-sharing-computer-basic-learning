## 白盒测试

- **形象理解**：把被测程序看作一个**透明的白（或玻璃）盒子**。测试人员需要了解内部结构、代码逻辑和实现细节。
    
- **关注点**：代码的覆盖率和内部执行路径是否正确。
    
- **测试人员**：通常由开发人员或懂代码的白盒测试工程师执行。
    
- **常用方法**：语句覆盖、判定覆盖、条件覆盖、路径覆盖、循环测试等。
    
- **典型例子**：
    
    - 测试一个排序函数：你要去查看代码中的每一个分支（如if-else、for循环），设计测试数据来执行到每一条语句、每一个分支路径。比如制造一个数组本已是升序的情况，来测试代码是否走了“优化路径”。
        
    - 测试登录功能：你要看代码里是否有“密码尝试次数超过5次就锁定账户”的逻辑，然后设计测试去验证这个逻辑是否被正确执行。
        
- **主要优点**：能发现代码深处的逻辑错误，促进代码清洁和优化。
    
- **测试原则：**
（1）程序模块中的所有独立路径至少执行一次
（2）在所有的逻辑判断中，取“真”和取“假”的两种情况至少都能执行一次
（3）每个循环都应在边界条件和一般条件下各执行一次
（4）测试程序内部数据结构的有效性等
## 黑盒测试

- **形象理解**：把被测程序看作一个**不透明的黑盒子**。测试人员只关注输入和输出，不关心内部如何实现。
    
- **关注点**：程序的功能是否符合需求规格说明。
    
- **测试人员**：通常由测试人员或业务用户执行，不需要懂编程代码。
    
- **常用方法**：等价类划分、边界值分析、因果图、场景法、错误推测法等。
    
- **典型例子**：
    
    - 测试一个登录功能：输入正确的用户名和密码，检查是否能登录成功；输入错误的密码，检查是否提示“用户名或密码错误”。你完全不需要知道程序是用什么语言写的、具体怎么校验密码的。
        
    - 测试计算器：输入“2 + 3”，检查输出是不是“5”，不需要知道加法功能的代码如何实现。
        
- **主要优点**：站在用户角度测试，覆盖功能需求，测试设计不依赖代码。
    
- **主要缺点**：可能遗漏代码内部的逻辑错误（如某条特定路径从未被执行）。
### 核心区别总结

| 维度           | 黑盒测试           | 白盒测试           |
| ------------ | -------------- | -------------- |
| **视角**       | 用户/外部视角        | 开发者/内部视角       |
| **依据**       | 需求规格说明书        | 源代码、详细设计       |
| **是否需要编程知识** | 一般不需要          | 需要             |
| **主要测试目标**   | 功能正确性、易用性      | 代码结构、逻辑覆盖、内部质量 |
| **典型场景**     | 系统测试、验收测试、功能测试 | 单元测试、集成测试      |
## 单元测试

针对软件中的最小可测试单元（如函数、类、模块）进行验证，主要检查内部逻辑、数据流、边界条件等，**不涉及模块之间的交互**。通常由开发人员执行，使用桩模块或驱动模块模拟外部依赖。

## 系统测试

在集成完成后，对整个系统进行测试，验证系统是否符合需求规格说明。它关注系统功能、性能、安全性等整体特性，**虽然可能暴露出接口问题，但并非专门针对接口**，更侧重于端到端的业务场景。

## 验收测试
                   
由用户或客户执行，确认系统是否满足业务需求和合同规定。它验证系统在实际使用环境中的可用性，**不专门定位模块间的接口缺陷**，而是从用户视角判断是否接受系统。

## 集成测试

专门用于发现模块之间接口、数据传递、调用关系、全局数据结构等方面的问题。它将在单元测试完成的模块组合起来，测试它们能否协同工作，例如参数类型不匹配、返回值错误、顺序依赖等。**因此，集成测试是最适合发现模块间接口问题的测试阶段**。

## 面向对象测试

+ 算法层:测试类中定义的每个方法，基本相当于传统软件测试的单元测试。
+ 类层:测试封装在同一个类中的所有方法与属性之间的相互作用。可以认为是面向对象测试中特有的模块测试。
+ 模板层:测试一组协调工作的类之间的相互作用。大体上相当于传统软件测试中的集成测试。
+ 系统层:把各个子系统组装成完整的面向对象软件系统。
